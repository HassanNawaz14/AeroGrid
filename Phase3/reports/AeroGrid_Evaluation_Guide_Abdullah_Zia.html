1. Project Overview & Architecture Scope

AeroGrid is an enterprise-grade cloud data warehouse built for Unmanned Aircraft Systems (UAS / drones) and Advanced Air Mobility (AAM). The system solves a critical operational challenge: commercial drone corridors, vertiports, and low-altitude airspaces operate across completely siloed data streams—flight ADS-B telemetry, meteorological observations, and regulatory airspace restrictions. AeroGrid unifies these streams into a high-performance star schema on Neon Serverless PostgreSQL.

Three-Tier Warehouse Architecture
  • project_staging: Raw ingestion landing buffer, schema normalization, batch reject classification (stg_reject).
  • project_dw: Star schema consisting of 6 dimensions and 4 fact tables with deterministic surrogate keys.
  • project_reporting: Standardized gold analytical views, corridor density metrics, and BI reporting marts.
Core Non-Negotiable Tenets
  • 100% Real Public Data: Tartan ADS-B (CMU), NOAA/IEM METAR weather, and FAA UDDS ArcGIS REST. Zero synthetic rows.
  • Fail-Closed DQ: Reconciles input counts = accepted staging + rejected staging. Idempotent re-runs.
  • Missing Coverage Invariant (D-029, D3-009): Explicit distinction between measured zero and unobserved sensors.

3.2 Hardening Track WP-P3-H2: FAA ArcGIS Quota Mitigation & Caching

The Operational Challenge & Root Cause
FAA UDDS ArcGIS FeatureServer endpoints enforce rate limits. Repeated CI runs or scheduled ETL pipelines triggered HTTP 429 ("Too Many Requests"), HTTP 503, or JSON error bodies ({"error": {"code": 400, "message": "..."}}). Because regulatory airspace polygons (Class_Airspace, Special_Use_Airspace) are static and only update every 28 days on the FAA AIRAC cycle, repeatedly querying live endpoints was inefficient and risked breaking the entire pipeline.

Architecture Implemented by Member B (Decision D3-016):

  • ArcGisCache (File-Backed JSON Caching): Implemented in Phase2/etl/quota_mitigation.py. Caches FeatureCollection responses with configurable TTL (default 24 hours). Uses atomic rename (.tmp -> .json) to prevent partial reads and provides emergency stale-cache fallback if live servers fail.
  • BackoffBudget (Bounded Exponential Backoff with Jitter): Computes dynamic retry delays:
    Delay = min(MaxDelay, BaseDelay × 2attempt − 1) × (0.5 + 0.5 × rand())
    Detects HTTP 429, 503, and JSON error bodies, retrying up to a configured budget to prevent API rate spikes.
  • Graceful Degradation / Optional Airspace Mode: Enhanced Phase2/etl/fetch.py and Phase2/etl/faa_restrictions.py. When AEROGRID_OPTIONAL_AIRSPACE=1, if live FAA endpoints are down and no cache exists, the system logs a structured warning and allows weather and flight telemetry ingestion to succeed.
  • Automated Test Suite: Created Phase3/tests/test_faa_quota_mitigation.py with 6 unit tests validating cache hits/misses, TTL expiration, stale fallback, backoff delay calculations, and graceful degradation (100% pass rate).

4. Architectural Highlights & Project "Bonus Points"

1. Honest Indexing Verdict (D3-010, D3-011)
In WP-P3-05, rather than claiming artificial query speedups, three candidate indexes were measured using EXPLAIN (ANALYZE, BUFFERS) inside rollback transactions. Runtime deltas were +0.36% to +0.58% (neutral). Following engineering integrity, the team applied zero indexes and documented the findings.
2. Explicit Coverage vs. Zero Events (D3-009)
The schema and views strictly differentiate between "measured zero" (sensors active, no flights detected) and "missing coverage" (station offline or outside study bounds). Null metrics display as NO_COVERAGE.
3. Strict 10 MiB Artifact Size Guard (D3-008)
Automated via Phase3/scripts/package_artifacts.py and CI. Any deliverable ≥ 10 MiB is routed to GitHub Actions release bundles and fails Git commits, preventing repository bloat.
4. Single BI Ownership Rule (D3-002)
Eliminated merge conflicts and divergent KPI formulas by assigning sole authorship of BI artifacts (Power BI PBIX, screenshots, report) to Member E, with strict peer review by Members B, A, C, and D.

5. High-Yield Viva / Evaluation Defense Q&A

The following curated questions represent the most critical technical and architectural concepts an evaluator or professor is likely to examine regarding Member C (Phase 2) and Member B (Phase 3).

Q1 Why did Member C implement a `-1` surrogate key in every dimension instead of allowing NULL foreign keys in fact tables?
Answer: In dimensional modeling (Kimball methodology), NULL foreign keys in fact tables cause outer join overhead, break referential integrity constraints, and result in silent data omission during SQL aggregations and OLAP group-bys. By seeding a deterministic -1 row (e.g. UNKNOWN_VEHICLE, UNKNOWN_SITE) in every dimension, every fact record successfully resolves its foreign key. This cleanly separates "unmapped/unidentified source entity" from database query errors and guarantees 100% referential integrity without losing unlinked telemetry.
Q2 Why did Member C use `BIGINT GENERATED ALWAYS AS IDENTITY` instead of `SERIAL` for surrogate keys?
Answer: SERIAL in PostgreSQL is a legacy pseudo-type that merely creates an underlying sequence and sets a default value, allowing accidental or unauthorized explicit inserts that bypass the sequence. GENERATED ALWAYS AS IDENTITY complies strictly with SQL:2003 standards, prevents client applications from inadvertently inserting arbitrary surrogate keys, guarantees true monotonically increasing uniqueness, and is fully optimized for Neon PostgreSQL's distributed storage architecture.
Q3 What are the 4 core fact tables in AeroGrid, and what are their specific analytical grains?
Answer: (1) fact_tracking_position: Grain is one timestamped ADS-B telemetry message per aircraft; (2) fact_flight_encounter: Grain is one detected pair of airborne vehicles within close proximity thresholds (≤ 0.5 NM horizontal, ≤ 500 ft vertical); (3) fact_hourly_airspace_occupancy: Grain is one hour × grid cell × site recording distinct vehicle counts and total airborne flight minutes; (4) fact_restriction_compliance: Grain is one aircraft flight observation intersecting an active FAA Temporary Flight Restriction (TFR) polygon window.
Q4 How does `dim_time` work, and why was it generated as a derived hourly spine rather than a standard calendar?
Answer: Commercial aviation and drone operations function at hourly and sub-hourly temporal granularity, not merely daily. Member C derived dim_time by generating an hourly spine covering the active observation window (2022-01-01 00:00:00 UTC through 2022-01-07 23:00:00 UTC; 168 rows + 1 unknown row = 169 rows). This avoids requiring Neon database superuser calendar extensions, supports direct temporal joins from UTC timestamps, and enables granular peak vs. off-peak flight pattern analysis.
Q5 How does trajectory journey segmentation work when converting raw ADS-B positions into flights?
Answer: In Phase 2 (WP-06), trajectory positions for each vehicle are time-ordered. A new journey is segmented whenever (1) a vehicle experiences a temporal gap exceeding 30 minutes without messages, or (2) a vehicle transitions from ground state to airborne state. Each journey receives a deterministic identifier, allowing flight metrics (total journey duration, distance traveled, average speed, max altitude) to be aggregated cleanly.
Q6 What operational issue triggered Hardening Track WP-P3-H2, and how does your solution solve it?
Answer: FAA ArcGIS FeatureServers enforce external rate limits and quota caps, frequently returning HTTP 429 ("Too Many Requests") or JSON error bodies during rapid scheduled runs or CI verification workflows. Member B resolved this under Decision D3-016 by introducing ArcGisCache and BackoffBudget. Since regulatory airspace boundaries update only once every 28 days on the FAA AIRAC cycle, caching GeoJSON responses for 24 hours eliminates redundant network calls. If live servers fail, the system falls back to stale cache or gracefully degrades without crashing the entire telemetry pipeline.
Q7 Why did you include randomized jitter in your exponential backoff formula for WP-P3-H2?
Answer: Standard exponential backoff causes all failed client requests to retry at identical mathematical intervals (e.g., exactly at 2s, 4s, 8s). When multiple batch jobs, CI runners, or workers run concurrently, this produces a "thundering herd" problem, slamming the rate-limited API in synchronized waves. By adding randomized full jitter (scaling between 50% and 100% of the bounded interval), retries are smoothly distributed across time, maximizing recovery probability without overwhelming the upstream server.
Q8 What does Decision `D3-009` ("empty-means-missing-coverage") mean, and how did Member B verify it?
Answer: In flight safety and business intelligence, an empty result set or zero count can mean two completely different things: (1) an active sensor observed zero aircraft movements, or (2) the sensor was offline, unconfigured, or out of range. D3-009 mandates that zero events must never be assumed when coverage is missing. Member B verified that all analytical SQL queries and gold views use explicit dimension outer joins and case logic, outputting NO_COVERAGE for unmonitored sites (e.g. KAGC, which had weather but no ADS-B receivers in January 2022).
Q9 What is the BI Ownership Rule (`D3-002`), and how did it affect team coordination?
Answer: To prevent conflicting KPI calculations, broken Power BI relationships, and Git merge conflicts across binary PBIX files, Decision D3-002 assigned sole authorship of all BI deliverables (PBIX dashboard, screenshots, insights report, presentation) to Member E. All other team members (A, B, C, D) acted as formal peer reviewers. Member B reviewed source licensing, staging compatibility, and reporting view schemas, signing off on evidence rather than editing binary report artifacts.
Q10 Why did the team decide NOT to create indexes in Phase 3 under Decision `D3-011`?
Answer: In WP-P3-05, the team evaluated three candidate B-Tree indexes on fact_tracking_position. In verify mode, EXPLAIN (ANALYZE, BUFFERS) showed identical query execution plans, identical sequential page scans, and execution time deltas of +0.36% to +0.58% (neutral/within run noise) because the table size (27,479 rows) fits comfortably in Postgres buffer memory. Applying unnecessary indexes would consume write overhead and disk storage without query benefit. Per D3-011, the team honestly documented the neutral verdict and deferred index creation until table size warrants it.
Q11 How do you prove that no synthetic data or secret credentials were committed?
Answer: (1) All 27,479 flight tracking facts reconcile back to Tartan Aviation raw trajectory CSVs via deterministic journey segmentation. (2) Zero passwords, tokens, or connection strings are stored in code or repository configs; Neon access is restricted to the aerogrid_reader role in Power BI and protected GitHub Actions secrets. (3) Phase3/scripts/package_artifacts.py executes an automated regex secret scanner before every build, returning PASS with zero violations.
